# XolveManager Technical SEO Implementation Plan

**Audit date:** 2026-10-31  
**Project:** XolveManager  
**Production URL checked:** `https://xolvemanager.vercel.app/`  
**Mode:** Read-only inspection and prioritized planning. No code, configuration, or business logic was changed; nothing was deployed.

## Executive summary

The local source contains a reasonable technical SEO foundation: a server-rendered public homepage, a canonical origin helper, homepage Open Graph/Twitter metadata, `WebSite` and `SoftwareApplication` structured data, generated robots/sitemap routes, and `noindex` directives on application/auth/support/draft-policy pages.

Production does not currently serve that foundation. At the time of this audit, `/` returned HTTP 200 but had title `XolveManager`, an older product description, `noindex, nofollow`, no canonical link, and no observed JSON-LD. `/robots.txt` and `/sitemap.xml` both returned 404. The production `/login`, `/signup`, `/dashboard`, `/customers`, and a synthetic non-customer record path returned HTTP 200 and `noindex, nofollow`; those responses are consistent with app-shell routes, not evidence that private records were exposed. The production/source mismatch is the main SEO blocker and should be investigated as a deployment/build-target issue before making further SEO code changes.

The app is built with Next.js 16 App Router and React 19. The homepage is a server component and its meaningful content is in the initial HTML in local source. The authenticated business application is intentionally client-rendered behind a local-session check and reads records from the browser; it should remain non-indexable and need not be server-rendered for SEO. Local authentication is explicitly **not server-side authorization** and robots metadata is not an access-control mechanism.

No live Core Web Vitals, Lighthouse score, Search Console data, production image transfer sizes, or bundle-size report were obtained. The performance section separates measured source facts from work still needed.

## Audit scope and evidence notes

- Production HTTP requests were made on 2026-10-31 to `/`, `/robots.txt`, `/sitemap.xml`, `/login`, `/signup`, `/dashboard`, `/customers`, and `/customers/seo-audit-check-no-record`.
- The production response for `/` was HTTP 200 with title `XolveManager`, description “XolveManager is a business management dashboard for customer records, subscriptions, sales, payments, service accounts, renewals, notifications, and reports.”, and robots `noindex, nofollow`. No canonical link or JSON-LD was observed in the response.
- Production `/robots.txt` and `/sitemap.xml` returned 404.
- The production app/auth route probes returned HTTP 200 and `noindex, nofollow`; the probe did not access any real customer record.
- Local-source route probes returned HTTP 200 for `/`, `/robots.txt`, `/sitemap.xml`, `/legal/privacy`, `/legal/data-backup`, `/login`, `/signup`, `/dashboard`, `/settings`, `/legal/terms`, and `/support`. Local `/privacy` returned a 307 redirect to the canonical privacy route.
- These observations establish a production/source mismatch, but do **not** establish which commit or deployment configuration is live, whether an edge cache is involved, or why the mismatch exists. No deploy, CDN purge, or Search Console inspection was performed.

### Private-route protection and privacy

- App route metadata is an indexing directive, not access control.
- `ClientAppShell` checks local session state in the browser, then conditionally renders the app. It redirects unauthenticated users in client-side history; `src/services/localAuthService.ts` stores owner/session data locally.
- `docs/LOCAL_FIRST_BETA_NOTICE.md` and `docs/LOCAL_AUTH.md` explicitly state there is no server-side authentication or security boundary. Business data resides in browser storage, rather than a server-side customer-record API in the reviewed source.
- The initial server output of the authenticated app route is the launch shell while the client checks the local session; it is not a server-rendered customer record page.
- No personal/customer data was requested or observed in the tested route metadata. This limited SEO review is not a penetration test or a certification that every deployment/network/logging surface is private.
- Preserve the local auth flow; do not attempt to make private browser-local screens indexable. If server-hosted shared business data is introduced in the future, server authorization and privacy review must precede SEO exposure.

## 4. Structured data

- **Present in local homepage source:** JSON-LD `WebSite` and `SoftwareApplication` in `app/page.tsx`. The software description is feature-focused; the category is `BusinessApplication`; operating system is `Web`.
- **Not observed in production:** The production homepage response had no `application/ld+json` script.
- **Organization:** Do not add until the owner verifies the operating organization/legal entity, approved name, and any public address/URL/contact. No organization details or `sameAs` social URLs should be invented.
- **SoftwareApplication:** Existing type is appropriate as descriptive structured data. Keep name/category/description/image consistent with visible copy. Do not add fabricated price, offer, aggregate rating, review count, download count, or availability claims.
- **WebSite:** Existing type is appropriate for the verified canonical origin and site name.
- **BreadcrumbList:** Not necessary for the single-page homepage. Consider only on future multi-level public content pages if a visible, crawlable breadcrumb is implemented and matches the actual hierarchy.
- **Validation:** Parse JSON-LD from production HTML; validate syntax and supported properties with Schema.org validator and Google Rich Results Test after deployment. Neither rich-result eligibility nor ranking effects are guaranteed.

## 7. Recommended implementation order

1. **Establish the live deployment.** Confirm the intended Vercel project, root directory, branch/commit, build command, environment variables, aliases and cache behavior. Compare that deployment with the reviewed source. Do not change indexability blindly.
2. **Resolve the homepage indexation blocker.** Once the intended public homepage is confirmed, make production serve the reviewed page and its explicit `index, follow` metadata, canonical, social metadata and structured data.
3. **Restore and verify discovery routes.** Confirm `/robots.txt` and `/sitemap.xml` return 200 from the production deployment. Keep the sitemap restricted to reviewed, canonical public pages.
4. **Run the route/privacy matrix.** Verify app/auth/support/draft routes remain noindex, sitemap excludes them, and no customer records or identifiers are embedded into generated metadata/content. Keep client local authentication unchanged.
5. **Approve public legal/trust copy.** Obtain owner/legal review before treating technical privacy/data disclosures as final public policies.
6. **Validate aliases and canonical host.** Test HTTPS, host aliases, slash behavior, query variants and `/privacy` redirect against the confirmed production domain.
7. **Measure performance and accessibility.** Establish reproducible mobile/desktop baselines before making image/font/bundle changes. Repeat the earlier responsive spot check as part of broader testing.
8. **Optional enhancements.** Consider translated public pages, additional schema types, or image changes only when there is approved content and evidence to justify them.
9. **Post-release monitoring.** After an approved deployment, verify in Google Search Console and monitor indexing/crawl reports. No indexing, ranking, or performance result is implied by a deployment or local build.

## 8. Testing strategy

### Local pre-release

- `npm test`
- `npm run lint`
- `npm run build`
- `git diff --check`
- Smoke-test `/`, `/robots.txt`, `/sitemap.xml`, `/legal/privacy`, `/legal/data-backup`, `/privacy`, `/login`, `/signup`, `/dashboard`, `/settings`, `/support`, draft policy routes, and an unknown route.
- Inspect raw initial HTML, not only the hydrated DOM, for the homepage H1/copy/schema and for absence of customer data.
- Assert intended sitemap allowlist and robots sitemap URL; check noindex directives on private and draft routes.
- Test title, description, canonical, Open Graph/Twitter metadata, language and heading hierarchy per route.
- Verify client-side authentication paths still behave as before; no SEO implementation should change the local storage/auth model.

### Production after approved deployment

- Request each public/representative route over HTTPS and record status, redirect chain, final URL and headers.
- Verify `/` returns 200 and intended content, has no `noindex`, declares the canonical host, and includes the expected title/description, OG/Twitter tags, H1 and JSON-LD in initial HTML.
- Verify `/robots.txt` and `/sitemap.xml` return 200; parse sitemap XML and ensure only canonical reviewed public pages are listed.
- Verify login/signup/app/support/draft-policy pages remain `noindex`; ensure those paths and record-detail URLs do not appear in sitemap.
- Check `/privacy` redirects once to `/legal/privacy`; check HTTP-to-HTTPS and configured host aliases without loops or duplicate indexable versions.
- Verify social image URL returns an image with expected dimensions and that the browser/social metadata is consistent with visible copy.
- Measure mobile and desktop Lighthouse/Web Vitals after deployment; report measured values with device, location, date and test environment. Do not extrapolate a single lab run into a global performance claim.
- Use Search Console URL Inspection and sitemap reports after owner verification; record actual crawl/index outcomes rather than assuming them.
